# 2주차 RAG 학습·실습 진행안

검토일: 2026-10-15. 기준: 사용자가 참조한 「RAG 청킹 학습 자료 찾기」 채팅의 주차별 계획.

## 1. 범위

2주차는 **임베딩/청크/전처리: 임베딩 모델·벡터 DB 선정, 기본 RAG 구축, 청킹 전략·하이브리드 검색 비교**입니다.
GPTQ INT4 양자화는 이 주차의 범위가 아닙니다.

후속 일정은 3주차 vLLM + RAG, 4주차 RAG Tool을 사용하는 단일 LangGraph 에이전트,
5주차 Supervisor와 전문 에이전트로 확장하는 순서입니다.
이번 문서는 진행 방법 검토안이며 구현·실험 완료 보고서가 아닙니다.

사용자의 1차 완료 설명과 현재 폴더의 후속 벤치마크 결과·보고서를 기준으로,
과거 AGENTS.md의 'seq32 진행 중' 상태를 이번 계획의 현재 상태로 사용하지 않습니다.
기존 27B 벤치마크와 별도 7B FP8 양자화 자료를 RAG 품질 실험 결과로 섞지 않습니다.

## 2. 목표와 흐름

> 같은 내부 문서를 다르게 잘랐을 때, 어떤 방식이 답변에 필요한 근거를 더 잘 검색하는지 실제 수치로 비교한다.

```text
문서 → 텍스트 추출·정리 → 청킹 → 임베딩 → Milvus 저장
질문 → 같은 모델로 임베딩 → 근거 검색 → LLM 답변 → 검색·답변 평가
```

첫 실습에서는 검색 결과에 문서명·페이지/절·청크 본문을 함께 출력합니다.
검색 단계가 잘못됐는지, 근거가 맞아도 답변 생성이 잘못됐는지 구분할 수 있어야 합니다.

## 3. 환경 선택 제안

| 구성 | 시작 제안 | 이유 |
|---|---|---|
| 실행 환경 | 기존 Linux 서버, 별도 Python 3.11 rag-env를 우선 검토 | 교재의 권장 Python 버전. vllm-env/quant-env의 Python 3.10과 패키지는 유지 |
| 임베딩 | BAAI/bge-m3 후보 1개로 우선 고정 | 다국어·1024차원. 모델 선정과 청킹 비교를 동시에 하지 않음 |
| 임베딩 실행 | 2주차는 Python 라이브러리 호출, 소규모는 CPU 우선 | 임베딩 API 서빙 설정을 3주차로 분리 |
| 벡터 DB | Milvus. 첫 검색은 Lite도 가능, 하이브리드 단계의 최종 실행 형태는 기능 지원 확인 후 결정 | Milvus 공식 입문 예제를 사용하되 Lite/Standalone의 기능을 동일하다고 가정하지 않음 |
| 답변 생성 | 기존 Qwen/Qwen3.8-27B-FP8의 로컬 API를 사용할 수 있으면 재사용 | 모델 변경으로 인한 답변 차이를 청킹 효과로 오해하지 않음 |
| 평가 | 먼저 정답·근거가 있는 질문과 사람이 확인하는 기준표 | 초기 단계에서 평가용 LLM/API까지 추가하지 않음 |

이 표는 제안이며 실제 설치·기동은 수행하지 않았습니다.
Windows 작업 공간의 127.0.0.1을 GPU 서버 주소로 사용하지 않습니다.
Milvus 공식 RAG 튜토리얼은 OpenAI 임베딩·LLM을 사용하는 예제입니다.
로컬 모델 실습에서는 해당 호출 부분을 교체하며 API 키·클라우드 서비스는 필수로 하지 않습니다.

CPU에서의 처리 속도는 측정 전입니다. GPU를 사용하려면 27B LLM의 실제 VRAM 사용량을 먼저 확인하고,
동시에 들어간다고 가정하지 않습니다. 초기 문서 벡터는 필요시 LLM을 내린 상태에서 생성할 수 있습니다.
BGE-M3의 dense 임베딩부터 시작합니다. BGE-M3의 learned sparse 출력과 BM25는 서로 다른 방식입니다.

## 4. 5단계 진행 순서

| 단계 | 학습·실습 | 완료 확인 |
|---|---|---|
| 1. 문서 준비 | 문서 1개로 제목·본문·표 추출 확인. 반복 머리말/꼬리말 정리. 이후 5~10개로 확대 | 원문과 추출 텍스트를 나란히 확인하고 페이지/절 정보를 추적 가능 |
| 2. 첫 검색 | 재귀 청킹 → 임베딩 → Milvus 저장 → 질문 검색 | 질문 1개에 대해 근거 청크와 출처를 직접 확인 |
| 3. 기본 RAG | 검색한 근거를 프롬프트에 넣고 로컬 LLM 호출 | 답변과 출처 출력, 근거 없는 질문에는 모른다고 응답 |
| 4. 청킹 비교 | 고정 토큰·재귀를 먼저 비교하고 문서 구조·시맨틱 분할 추가 | 공통 질문에 대한 검색 결과·답변·시간을 전략별 저장 |
| 5. 검색 개선 | 동일 청킹에서 dense 단독과 dense+BM25 비교. Reranker는 그다음 ON/OFF | 개선된 질문과 악화된 질문을 수치 및 원문 근거로 설명 |

시맨틱 청킹은 문장 임베딩 등을 추가로 사용하므로 청크 생성 시간도 따로 기록합니다.
제목·절 기반 청킹은 구조가 보존된 문서에 적용합니다. PDF에서 제목 구조가 사라지면
자동으로 올바른 구조를 얻었다고 간주하지 않습니다. 스캔 PDF의 OCR 필요 여부는 문서 확인 후 결정합니다.

## 5. 처음 비교할 조건

아래 수치는 새 RAG 실험의 **시작 제안**입니다. 이전 vLLM 부하 테스트 설정을 수정하는 것이 아닙니다.

- 문서: 먼저 1개로 작동 확인, 비교 단계에서는 같은 5~10개를 사용.
- 질문: 정답과 원문 근거를 작성한 공통 질문 20개로 시작.
- 청킹: 고정 길이·재귀는 512토큰, overlap 64토큰을 시작 후보로 사용.
  같은 토큰 계산기를 쓰고, 문자 512개와 토큰 512개를 혼동하지 않습니다.
- 구조·시맨틱 청킹: 경계를 우선 보존하되 최대 길이 제한을 기록.
  길이가 달라지면 실제 청크 길이 분포와 전달된 근거 토큰량을 함께 기록.
- 검색: 동일한 임베딩 모델·정규화·거리함수, 최종 top-k=5를 시작 후보로 고정.
- 청킹 전략마다 별도 collection/run_id로 저장. 임베딩 모델 변경 시 문서 벡터를 다시 생성.
- 답변: 같은 모델·프롬프트·생성 설정. 근거에만 기반해 답하고 출처를 표시하도록 지시.
- 기존 LLM의 max-model-len=4096을 사용할 경우 입력(지시문+질문+근거)+최대 출력이
  4096 이하인지 LLM 토크나이저로 확인. 근거 예산 2048토큰, 최대 출력 256토큰을 시작 후보로 사용.
  임베딩 토크나이저의 길이와 LLM의 길이는 같지 않을 수 있음.
- top-k 검색 결과 전체와 실제 답변에 사용한 근거를 별도로 기록.
  근거 예산 때문에 일부 청크를 제외했다면 해당 차이도 남김.
- overlap 변경, 하이브리드 추가, Reranker 추가는 한 번에 하나씩 수행.
- 하이브리드는 같은 문서에서 dense와 BM25 후보를 얻고 순위 결합으로 시작.
  한국어 분석기의 띄어쓰기·고유명사 처리와 BM25 설정을 기록.

메타데이터에는 doc_id, 파일명, 페이지/절, 원문 위치, chunk_id, strategy, 청크 길이를 포함합니다.
정답 근거는 특정 전략의 chunk_id 대신 원문 문서·페이지·문장/위치로 기록합니다.
청킹마다 chunk_id가 달라져도 같은 정답 근거를 기준으로 평가할 수 있어야 합니다.

## 6. 평가와 결과물

| 항목 | 시작용 평가 방법 |
|---|---|
| 근거 검색 성공률 Hit@5 | 정답 근거가 검색 상위 5개에 하나 이상 포함된 질문 수 / 답할 수 있는 질문 수 |
| 답변 정확도 | 미리 정한 정답·필수 내용 기준으로 동일 질문을 채점. 맞음/부분/틀림 기준 명시 |
| 근거 충실성 | 답변의 주장이 실제 검색 근거로 뒷받침되는지 확인 |
| 시간 | 문서 적재/임베딩 시간, 질의 검색 시간, 답변 생성 시간을 분리 |
| 비용·규모 | 청크 수, 길이 분포, 실제 근거 토큰량, 선택한 경우 모델 메모리 |

Hit@5를 Ragas의 Context Recall과 같은 지표라고 부르지 않습니다.
단일 질문 정답이나 데모 성공만으로 품질 개선을 주장하지 않습니다.
질문 중 '문서에 답이 없음' 유형은 검색 Hit@5 분모에서 분리하고 적절한 답변 보류 여부를 평가합니다.
시맨틱 청킹이나 Reranker가 항상 우수하다고 가정하지 않습니다.

2주차 말에는 다음을 남깁니다.

1. 문서 적재부터 검색·답변까지 실행되는 기본 코드와 환경 버전.
2. 공통 질문·정답·원문 근거 목록.
3. 청킹 전략별 검색 결과·답변·시간 및 비교표.
4. 하이브리드 검색과 Reranker의 추가 효과를 구분한 결과.
5. 대표 성공/실패 사례와 3주차에 연결할 항목.

최종 청킹 비교 보고서는 참조 채팅의 일정대로 3주차 vLLM 연결 검증 후 마무리합니다.
이번 요청에서는 Word 보고서나 GPU 배포를 새로 수행하지 않습니다.
