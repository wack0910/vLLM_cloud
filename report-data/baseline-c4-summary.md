# 최초 기준 측정: 동시 요청 한도 4, 1000개 요청 × 3회

출처: 사용자가 첨부한 콘솔 텍스트. 원본 JSON, 실행 당시 설정 사본, KV Cache 기록은 아직 받지 않았다.
아래는 요청 길이 목표 1024/128, 동시 요청 한도 4로 수행한 것으로 전달받은 결과이며,
실제 모델과 나머지 설정은 원본 JSON 및 설정 사본으로 최종 확인한다.

| 회차 | 성공 | 실패 | 소요 시간(s) | 평균 TTFT(ms) | p95 TTFT(ms) | 평균 TPOT(ms/token) | p95 TPOT(ms/token) | 출력 tok/s |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1000 | 0 | 1764.94 | 1066.75 | 1312.24 | 47.18 | 49.85 | 72.52 |
| 2 | 1000 | 0 | 1765.20 | 1067.31 | 1312.52 | 47.19 | 49.85 | 72.51 |
| 3 | 1000 | 0 | 1765.13 | 1067.27 | 1312.45 | 47.19 | 49.85 | 72.52 |

- 합계: 3000개 요청 성공, 실패 0개. 측정 구간 합계 5295.27초 = 약 88.25분.
- 회차별 수치의 산술평균: 소요 시간 1765.09초, 평균 TTFT 1067.11ms,
  평균 TPOT 47.1867ms/token, 출력 처리량 72.5167tok/s.
- 각 회차 입력 토큰 1,036,403개, 출력 토큰 128,000개. 평균 출력은 요청당 128개.
- 세 번의 집계 수치는 유사하다. 이 조건의 반복 일관성을 보여주지만 다른 부하의 안정성을 보장하지 않는다.
- KV Cache 사용률/용량은 제공되지 않았으므로 공란으로 둔다.
- Maximum request concurrency=4, Peak concurrent requests=8.00이라는 콘솔 표시 차이는 원본 그대로 보존하며 지표 정의 확인 전 실제 동시 처리 8개라고 해석하지 않는다.

## 시간 제약에 따른 실험 계획 변경

후보별 1000개 × 3회 대신, 160개 × 1회로 먼저 탐색한다.
입출력 목표 1024/128은 유지하되 서버 한도 8/16/32의 차이를 보기 위해
클라이언트 동시 요청 한도를 32로 고정한다. 따라서 현재 서버 구성에서도
새 빠른 기준 측정을 먼저 수행하고, 이 최초 동시 요청 4 결과와 튜닝 효과를 직접 계산하지 않는다.

동시 요청 4에서 160개의 순수 측정 시간을 선형 추정하면 약 282초(4.7분)이다.
이는 동일 처리율이 유지된다는 가정이며 서버 시작·모델 로딩·토크나이저 준비·워밍업 시간은 제외한다.
동시 요청 32의 시간은 아직 측정되지 않았고 8배의 시간 단축을 가정하지 않는다.

탐색 결과 중 기준 구성과 선택 후보 구성만 추가로 반복 확인한다.
작은 차이로 순위가 바뀌거나 실패/이상 지연이 있으면 해당 조건의 반복 측정을 우선한다.
160개 탐색 결과의 p95는 참고값이며 p99/장시간 안정성의 근거로 사용하지 않는다.
최종 Word 보고서는 최초 기준 측정과 빠른 탐색을 서로 다른 실험군으로 구분한다.
